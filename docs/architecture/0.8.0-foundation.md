# Sport Platform 0.8.0 Foundation

## Objective

Evolve Gestion Club from an Apps Script/Sheets rugby application into a multi-sport, multi-organization platform.

The current 0.7.37 deployment remains untouched while 0.8.x is developed in parallel.

## Environment strategy

- `feat/*`: development work
- `develop`: PRE
- `main`: PRO

Supabase projects are separated by environment:

- PRE: isolated database, auth, storage and Edge Functions
- PRO: isolated database, auth, storage and Edge Functions

No production data or production secrets are used in PRE.

## Target architecture

- GitHub: source of truth for code, migrations, tests and CI/CD
- Supabase: PostgreSQL, Auth, RLS, Edge Functions and metadata
- DocumentStorage abstraction:
  - PRE: Supabase Storage
  - PRO initially: Google Drive
- WhatsApp: interaction channel for availability, surveys, document requests and notifications
- Apps Script: legacy only; no dependency in the 0.8.x target architecture

## Core domain principles

1. A person is unique inside a tenant and can have multiple roles.
2. Rugby is a sport configuration, not the core data model.
3. Federation, association, club and academy share the same organization model.
4. Organization hierarchy is represented with parent/child relationships.
5. Operational access is explicit through tenant and organization user grants.
6. Players, families and referees do not need an account for every interaction.
7. Action Links will support secure no-login workflows.
8. All privileged actions are audited.

## Foundation scope

The first migration creates:

- tenants
- tenant_users
- organizations
- organization_users
- sports
- organization_sports
- seasons
- categories
- teams
- persons
- person_memberships

Later 0.8.0 migrations will add:

- events and participation
- documents and document requests
- licenses
- payments and account movements
- surveys
- action links
- communication jobs
- audit log
- RLS policies
- legacy import staging

## Storage policy

The domain stores document metadata independently from the binary storage provider.

`DocumentStorage` will support at least:

- `SupabaseStorageProvider`
- `GoogleDriveProvider`

This allows PRE to use Supabase Storage and PRO to use Google Drive initially without changing document workflows.
